# Regenerating docs/asyncapi.json

## Applies when

Adding or changing a kafka channel moses publishes to or consumes from, and
wanting `docs/asyncapi.json` to match.

**Not this if**: the REST documentation. That is swaggo, driven by
`main.go`'s `go:generate` and regenerated by the Dockerfile's `go generate
./...` -- no manual step.

## Two steps, because the generator is a separate module

`docs/asyncapi-gen/` has its own `go.mod`, so `go generate ./...` from the
repository root never reaches it. Run both steps from the repository root:

```
cd docs/asyncapi-gen && go generate ./...
npx --yes @asyncapi/cli@6.2.0 convert docs/asyncapi-gen/asyncapi.json -f asyncapi -t 3.0.0 -o docs/asyncapi.json
```

The generator reflects the message types with `swaggest/go-asyncapi` and
writes AsyncAPI 2.4.0 to `docs/asyncapi-gen/asyncapi.json` (gitignored, not
`docs/asyncapi.json`). The `asyncapi convert` CLI turns that into the 3.0.0
`docs/asyncapi.json` this repo commits, matching every other SENERGY service's
committed spec version. CI runs the same two steps and fails on a diff, so a
changed message type shows up as a CI failure rather than a stale spec.

## Expect a go.sum to drift

Because nothing exercises `docs/asyncapi-gen/` between changes, its `go.sum`
can go stale against the main module's dependencies. `go mod tidy` inside that
directory fixes it and pulls in no new direct dependency.

## The message shapes come from platform-connector-lib

Moses defines none of the message types itself -- they are
`platform-connector-lib`'s `model.ProtocolMsg`, `model.Envelope`,
`platform_connector_lib.DeviceTypeCommand` and
`connectionlog.DeviceLog`. A dependency bump that changes one of these
invalidates the committed spec silently until the two steps above are rerun.
